# 产品 / 视觉 / 前端 / 后端与任务模块说明

> 目标：统一团队对“职能分工”和“业务模块”的理解。  
> 结论：产品、视觉、前端、后端是职能视角；Product、Material、Script、Creation、Job 等是业务模块视角。两者不是同一层级，应该交叉协作。

## 1. 两种视角不要混在一起

### 职能视角

职能视角回答：

```text
谁负责什么类型的产出？
```

当前建议保留 4 个核心职能页：

```text
产品设计
视觉设计
前端设计
后端设计
```

它们分别关注：

- 产品设计：用户路径、业务价值、功能边界、异常流程、Demo 叙事。
- 视觉设计：界面气质、信息层级、布局、组件外观、状态表达。
- 前端设计：页面架构、组件拆分、状态管理、接口联调、交互实现。
- 后端设计：业务模块、API、数据模型、任务状态机、模型调用、失败重试。

### 业务模块视角

业务模块视角回答：

```text
系统需要具备哪些业务能力？
```

当前项目建议关注这些业务模块：

```text
Product
Material / Asset
Script
Creation
Job
AI Workflow
Analytics
Compliance
Demo / Submission
```

每个业务模块都需要从产品、视觉、前端、后端四个角度被审视。

例如“Script 剧本模块”：

- 产品设计：用户为什么需要剧本？能改哪些内容？P0 做到什么程度？
- 视觉设计：剧本卡片、分镜列表、编辑态如何呈现？
- 前端设计：组件如何拆？状态如何管理？调用哪个接口？
- 后端设计：Script 数据如何存？Prompt 如何生成？schema 如何校验？

## 2. 推荐飞书文档组织方式

保留职能页，但每个职能页内部按业务模块展开。

## 3. 四个职能分别应该写什么

### 3.1 产品设计

产品设计回答：

```text
用户是谁？
为什么需要这个功能？
用户如何从进入系统走到拿到视频？
P0/P1/P2 分别做什么？
```

本项目产品设计重点：

- 商家用户画像。
- 一句话业务价值。
- P0 主路径。
- 功能分级。
- 异常流程。
- Demo 叙事。
- 终稿提交材料中如何解释项目价值。

产品设计不需要写代码实现细节，但要定义清楚“做什么”和“为什么做”。

### 3.2 视觉设计

视觉设计回答：

```text
界面看起来是什么气质？
信息如何被看见？
状态如何被用户理解？
```

本项目视觉设计重点：

- 工作台整体布局。
- 素材输入区样式。
- 剧本与分镜卡片样式。
- 生成进度状态样式。
- 失败、完成、等待等状态表达。
- 视频预览区。
- 数据看板视觉方向。

视觉设计不负责决定后端怎么生成视频，也不负责接口怎么写。它负责让系统看起来清楚、可信、有完成度。

### 3.3 前端设计

前端设计回答：

```text
页面如何组织？
组件如何拆分？
状态如何流动？
如何和后端接口协作？
```

本项目前端设计重点：

- 路由设计：`/material`、`/script/:jobId`、`/creation/:jobId`。
- 组件拆分：商品表单、任务进度、剧本面板、分镜列表、视频预览。
- 状态管理：React Query 管服务端数据，Zustand 管编辑器本地态。
- 任务轮询：定时查询 `GET /api/jobs/:jobId`。
- 错误与重试交互。
- 视频预览与兜底视频。

前端设计比视觉设计更偏实现，但不等于后端逻辑。它重点关注浏览器里的页面、状态和交互。

### 3.4 后端设计

后端设计回答：

```text
业务能力如何被 API、数据模型、任务系统和模型调用承载？
```

本项目后端设计重点：

- `material / script / creation` 三大模块。
- P0 数据模型。
- Job 状态机。
- `jobs/processors`。
- `packages/ai` 模型调用边界。
- Prompt、schema 校验、trace。
- 失败重试和兜底模板。
- API Key 安全。

后端不是简单写接口，而是把“商品素材 -> 剧本分镜 -> 视频生成 -> 预览产物”组织成稳定的异步任务链路。

## 4. 需要做的任务模块与名称解释

下面这些任务名称建议在飞书和代码中尽量保持一致。

### 4.1 Product：商品模块

中文名：商品模块

解释：

```text
Product 表示商家要推广的商品。
```

它包含：

- 商品标题。
- 商品卖点。
- 目标人群。
- 商品主图。

为什么需要：

视频生成不是凭空生成，而是围绕某个商品展开。Product 是后续素材、剧本、任务和生成结果的业务起点。

P0 要做：

- 商品标题输入。
- 卖点输入。
- 目标人群输入。
- 商品主图 URL 或上传入口。

### 4.2 Material / Asset：素材模块

中文名：素材 / 资产模块

解释：

```text
Material 更偏原始素材，比如商品图、参考图、商品视频。
Asset 是系统内统一管理的资源，可以是上传素材，也可以是生成产物。
```

当前 P0 推荐用 `Asset` 统一承载：

- 商品图：`product_image`
- 最终视频：`final_video`
- P1 音频：`audio`
- P1 字幕：`subtitle`

为什么需要：

系统要管理文件 URL、来源、类型、元信息，不能把图片和视频散落在各个字段里。

P0 要做：

- 注册商品图为 `Asset(type=product_image)`。
- 保存最终成片为 `Asset(type=final_video)`。

P1/P2 可做：

- 素材标签。
- 素材切片。
- 素材检索。
- embedding 召回。

### 4.3 Script：剧本模块

中文名：剧本模块

解释：

```text
Script 表示 AI 生成的带货视频脚本，包括整体叙事、视觉风格和基础分镜。
```

它包含：

- 叙事框架。
- 视觉风格。
- 2-4 个 StoryboardShot。
- 原始 JSON。
- 版本号。

为什么需要：

剧本是商品信息和视频生成之间的桥梁。它让“模型生成”变得可解释，也让用户能看到视频为什么会这样生成。

P0 要做：

- 根据商品信息生成结构化剧本。
- 用 zod schema 校验输出。
- 展示剧本和基础分镜。

P1/P2 可做：

- 剧本重生成。
- Prompt 微调。
- 剧本版本对比。
- 模板化剧本。

### 4.4 StoryboardShot：分镜脚本单元

中文名：分镜 / 分镜脚本单元

解释：

```text
StoryboardShot 是剧本里的一个叙事 beat，不是 P0/P1 的视频渲染切片。
```

它包含：

- 画面描述。
- 运镜。
- 时长。
- 台词。
- 字幕。

为什么需要：

PRD 要求基础分镜。分镜也可以作为最终 12s 视频 prompt 的脚手架。  
P1 的“分镜级干预”可以通过修改某个 shot，再重新生成整条 12s 视频实现。

重要边界：

```text
P0/P1：分镜是脚本结构。
P2 可选：分镜才可能变成独立渲染片段。
```

### 4.5 Creation：视频创作模块

中文名：视频创作模块 / 成片模块

解释：

```text
Creation 负责把素材和剧本分镜转化为最终视频。
```

它关心：

- 一键成片。
- 生成视频 prompt。
- 调用 Seedance。
- 保存最终视频。
- 预览导出。

和 Script 的区别：

```text
Script 负责“写什么”。
Creation 负责“生成成片”。
```

P0 要做：

- 把 2-4 个 StoryboardShot 压缩成一个完整视频 prompt。
- 一次调用 Seedance 生成 12s 视频。
- 保存 `Asset(type=final_video)`。

P1/P2 可做：

- 分镜级改写后重新成片。
- TTS。
- 字幕。
- BGM。
- 多画幅导出。

### 4.6 Job：生成任务模块

中文名：生成任务模块 / 长任务模块

解释：

```text
Job 负责管理“生成视频”这个耗时过程的状态、进度、结果和失败原因。
```

为什么需要：

视频生成不是秒回的，前端不能一直卡在一个 HTTP 请求里等待。所以后端需要创建 `GenerationJob`，前端通过轮询查看进度。

它记录：

- 当前状态：`queued`、`running`、`completed`、`failed`
- 当前阶段：`script_generating`、`media_generating`
- 进度。
- trace。
- 错误信息。
- 最终视频 asset。

和 Creation 的区别：

```text
Creation 是“做视频”。
Job 是“管理做视频这件事的进度和结果”。
```

P0 要做：

- 创建生成任务。
- 记录任务状态。
- 记录生成阶段。
- 支持前端轮询。
- 失败时返回可读错误。

### 4.7 AI Workflow：AI 编排模块

中文名：AI 工作流 / 模型编排模块

解释：

```text
AI Workflow 负责把文本模型、视频模型、Prompt、schema 校验和 trace 串起来。
```

它包含：

- Seed 文本模型 provider。
- Seedance 视频模型 provider。
- Prompt 模板。
- 输出 schema。
- 一键成片 workflow。
- trace。
- 失败兜底。

为什么需要：

不能把模型调用散落在 controller 里。所有模型能力应该集中在 `packages/ai`，方便替换、调试和保护密钥。

P0 要做：

- 生成结构化剧本。
- 构造 12s 视频 prompt。
- 调用视频模型或 mock fallback。

P1/P2 可做：

- TTS。
- 多语言。
- Agent 编排。
- 爆款模板。
- A/B 出片。

### 4.8 Analytics：数据分析模块

中文名：数据分析 / 效果看板模块

解释：

```text
Analytics 用来展示生成因子和转化效果之间的关系。
```

它可以包含：

- mock CTR。
- mock 转化率。
- 不同剧本策略对比。
- 不同视觉风格对比。
- A/B 出片效果。

为什么需要：

PRD 鼓励关注电商转化效果。即使没有真实电商后台，也可以用 mock 数据展示业务意识。

P0 不必做。

P1/P2 可做：

- mock 数据看板。
- A/B variant 对比。
- 生成因子归因。

### 4.9 Compliance：合规模块

中文名：合规 / 来源声明模块

解释：

```text
Compliance 负责素材来源、版权风险和生成内容审核相关流程。
```

它可以包含：

- 素材来源声明。
- 公开视频只保存结构化分析，不复刻、不混剪。
- 生成内容审核状态。
- 版权风险提示。

为什么需要：

PRD 明确提到素材合规和来源声明。比赛中不一定要接真实版权服务，但需要能讲清楚工作流。

P0 不必做。

P2 可作为加分项。

### 4.10 Demo / Submission：演示与提交模块

中文名：演示与提交模块

解释：

```text
Demo / Submission 不是产品内业务功能，但它是比赛交付的关键任务。
```

它包含：

- 在线 Demo。
- 演示视频。
- README。
- 运行说明。
- 项目截图。
- 预生成成片。
- 提交字段。
- 答辩讲稿。

为什么需要：

比赛评审看重“可访问、可理解、可复核”。如果 Demo 路径不清楚，系统做出来也容易丢分。

P0 必须做：

- README。
- Demo Guide。
- 预生成样例。
- 可访问路径。

## 6. 推荐团队分工

如果是 2-3 人团队，不建议每个人都完全全栈，但每个人都应该理解完整业务链路。

推荐分法：

```text
成员 A：产品设计 + 前端主路径
成员 B：后端设计 + AI Workflow
成员 C：视觉设计 + Demo / Submission + Analytics
```

协作原则：

- 每个人有主责，不代表只看自己的部分。
- 所有人共用同一套业务模块名称。
- 重要边界写入“风险与决策记录”。
- 前后端接口以“接口与数据模型”页面为准。

## 7. 当前优先级

建议下一步按这个顺序推进：

1. 在飞书中确认这套职能页和业务模块名称。
2. 让团队成员认领职能主责。
3. 在每个职能页里按业务模块补内容。
4. 先完成 P0：Product、Material / Asset、Script、StoryboardShot、Creation、Job、AI Workflow。
5. 再考虑 P1/P2：Analytics、Compliance、A/B、Embedding、Agent。

一句话总结：

```text
职能页负责“怎么做”，业务模块负责“做什么”。
团队不是人人都要全栈，但人人都要对同一条业务链路有共同语言。
```
