# 团队协作与 6.10 终稿 OKR 建议

> 目标：在进入产品、视觉、前端、后端等模块研究之前，先把团队协作空间和 2026-06-10 终稿目标对齐，避免后续各模块发散。

## 1. 总体判断

当前项目已经有了终版架构方向：轻量 monorepo、`apps/web + apps/server` 两个部署物、server 内嵌 job processors、分镜作为剧本脚本结构、单次 Seedance 12s 出整片。

在正式推进模块研究前，建议先完成两件事：

1. 建立飞书协作文档空间，把需求、架构、产品、视觉、前后端设计、OKR 和提交材料统一管理。
2. 为 2026-06-10 终稿制定项目 OKR，并倒推出里程碑。

原因是：比赛项目最容易失败的点不是“没人做事”，而是“每个人都在做事，但对最终交付版本的理解不一致”。飞书文档和 OKR 应该成为团队的单一协作中枢。

## 3. 各页面职责

### 首页

首页只放高层导航和最新状态，不堆细节。

建议包含：

- 项目名称。
- 一句话业务价值。
- 当前版本目标。
- 负责人分工。
- 最新里程碑状态。
- Demo 链接、仓库链接、演示视频链接占位。

### 系统设计

内容来源：

- `docs/archive/arc_codex_r3.md`
- `docs/architecture.md`
- `docs/erd.md`

建议包含：

- 最终架构结论。
- 项目目录结构。
- “分镜是脚本结构，不是渲染单元”的关键取舍。
- `apps/web`、`apps/server`、`packages/shared`、`packages/ai` 的职责。
- P0 数据模型。
- 任务状态机。
- 模型调用边界。

### 产品设计

建议聚焦用户路径，而不是功能堆砌。

建议包含：

- 目标用户：TikTok Shop / 跨境电商商家。
- P0 主路径：商品图与卖点输入 -> 剧本/分镜 -> 一键成片 -> 预览导出。
- P1/P2 范围。
- 页面流程。
- 功能取舍。
- Demo 讲述路径。

### 视觉设计

建议包含：

- 视觉风格关键词。
- 核心页面截图或设计稿。
- 颜色、字体、间距、组件规范。
- 工作台布局原则。
- 演示视频中需要展示的视觉亮点。

注意：这是商家工作台，不是营销 landing page。视觉应该偏高效、清晰、可信，而不是重装饰。

### 前端设计

建议包含：

- 页面路由。
- 组件拆分。
- 状态管理。
- 任务轮询方案。
- 分镜展示与轻编辑方案。
- 视频预览与兜底视频策略。
- 与后端接口约定。

推荐页面：

```text
/material
/script/:jobId
/creation/:jobId
/dashboard
```

### 后端设计

建议包含：

- `material / script / creation` 三大模块。
- `jobs/processors` 设计。
- P0 API 清单。
- P0 五张表。
- 模型 provider 替换点。
- 任务 trace。
- 错误与重试策略。

### 接口与数据模型

这是前后端联调的唯一真源。

建议包含：

- API 路径。
- 请求 DTO。
- 响应 DTO。
- job status / stage 枚举。
- `Product`、`Asset`、`GenerationJob`、`Script`、`StoryboardShot` 字段。
- 示例请求和示例响应。

### 开发排期 / 里程碑

建议用倒排方式，从 2026-06-10 终稿往前拆。

建议字段：

```text
里程碑
负责人
开始日期
截止日期
验收标准
风险
当前状态
```

### 风险与决策记录

建议记录所有会影响范围的关键判断。

当前应写入：

- P0/P1 不做 FFmpeg 拼接。
- 分镜保留为剧本脚本结构。
- worker 逻辑保留，物理内嵌 server。
- P0 使用 5 张表。
- P0 素材检索用关键词/标签，embedding 放 P1/P2。
- 真实模型调用集中在 `packages/ai`。
- 必须准备 1-2 条预生成成片作为 Demo 兜底。

### Demo & 提交清单

建议提前准备，不要最后一天补。

应包含：

- 在线 Demo 链接。
- 体验账号或无登录说明。
- 演示视频链接。
- 源代码仓库链接。
- README / 运行说明。
- 架构说明。
- 项目截图。
- 1-2 条生成结果样例。
- 答辩讲稿或讲述顺序。

## 4. 6.10 终稿 OKR 建议

### Objective 1：在 2026-06-10 前交付可访问、可演示、可复核的 AIGC 带货视频生成系统

KR1：完成 P0 主链路：商品图/卖点输入 -> 剧本生成 -> 基础分镜 -> 一键成片 -> 预览导出。

KR2：Demo 可通过公开链接或本地一键启动访问，评委 3 分钟内能看到核心价值。

KR3：准备 1-2 条预生成成片作为现场兜底，实时生成失败时不影响答辩。

KR4：README、架构说明、运行说明、演示路径齐全。

KR5：保留项目需求文档、6 版架构讨论文档和最终架构文档，方便评审复核设计过程。

### Objective 2：体现清晰的全栈工程能力

KR1：前端完成素材输入、任务进度、剧本/分镜展示、视频预览四个核心界面。

KR2：后端完成 `material / script / creation` 三大模块和 `jobs/processors`。

KR3：完成 `packages/shared` 类型契约和 `packages/ai` 模型适配层。

KR4：完成 P0 五张表或等价数据结构：`Product`、`Asset`、`GenerationJob`、`Script`、`StoryboardShot`。

KR5：通过 `typecheck`、`lint`、`build`，保留最小 CI 配置。

### Objective 3：形成有说服力的 AI 创新叙事

KR1：明确并能解释“分镜作为脚本结构、单次 12s 成片”的技术取舍。

KR2：完成结构化剧本 JSON schema、Prompt 模板和模型调用 trace。

KR3：展示至少一个 P1/P2 创新方向：分镜级干预、A/B 出片、mock 数据看板、爆款模板或素材检索。

KR4：答辩材料能讲清楚业务价值、技术难点和后续扩展路径。

## 5. 里程碑建议

以 2026-06-10 为终稿日期，建议倒排：

### M1：协作与目标对齐

建议截止：2026-05-24

验收标准：

- 飞书文档目录完成。
- OKR 页面完成。
- 团队成员分工确认。
- `arc_codex_r3.md` 和 PRD 已归档。

### M2：P0 主链路跑通

建议截止：2026-05-29

验收标准：

- web 可创建生成任务。
- server 可生成结构化剧本和分镜。
- mock video 可预览。
- job 状态和 trace 可查看。

### M3：真实模型链路验证

建议截止：2026-06-02

验收标准：

- Seed 文本模型能稳定输出结构化 JSON。
- Seedance 能生成可播放 12s 视频。
- 记录耗时、失败率、并发限制。
- 至少产出 1 条真实生成样例。

### M4：Demo 完整体验

建议截止：2026-06-06

验收标准：

- P0 主路径可顺畅演示。
- 页面视觉与交互基本完成。
- 至少 1-2 条预生成成片可作为兜底。
- README、运行说明、Demo Guide 可用。

### M5：终稿与答辩材料

建议截止：2026-06-10

验收标准：

- 在线 Demo / 本地启动路径确定。
- 演示视频完成。
- 源代码仓库整理完毕。
- 提交材料字段齐全。
- 答辩讲述顺序确认。

## 6. 团队分工建议

如果是 2-3 人团队，建议不要按“页面”拆，而按交付责任拆：

```text
成员 A：产品 / 前端 / Demo 体验
成员 B：后端 / 模型链路 / job 状态机
成员 C：视觉 / 答辩材料 / 数据看板或 P1 创新
```

每个成员都应在飞书里维护自己负责页面的状态和阻塞项。

## 7. 当前优先级建议

下一步建议顺序：

1. 在飞书补齐页面结构。
2. 将本文件内容复制到 OKR 或开发排期页，团队审阅。
3. 明确 2026-06-10 之前每个里程碑的负责人。
4. 再开始产品设计、视觉设计、前端设计、后端设计的模块研究。

一句话：

```text
先让团队对“终稿长什么样”达成一致，再让每个模块往这个终稿收敛。
```
