# Open Source Acceleration Report for the AIGC Commerce Video Generator

## Executive Summary

The fastest path for this project is **not** to hunt for a full open-source “e-commerce AI video generator” and fork it. The practical shortcut is to **compose a small number of mature, TypeScript-friendly building blocks** on top of the stack you already have: your repo already uses a monorepo layout, React, Tailwind, `@dnd-kit/*`, TanStack Query on the web side, and Fastify, BullMQ, Redis, MinIO, Swagger, and Zod on the server side. That means the highest-leverage move is to **double down on the existing choices** and only add tools that reduce bespoke UI or infrastructure work. fileciteturn0file0 citeturn4view1turn5view0turn6view0

The **seven tools or patterns most worth adopting immediately** are these. **Uppy** gives you a production-grade upload UI for merchant assets with preview and resumability, instead of hand-rolling file upload UX. **React Hook Form + Zod** is the quickest way to make merchant-facing forms and keep them consistent with shared DTOs. **Keep dnd-kit and TanStack Query** because they are already in your repo and are the right primitives for sortable storyboard cards and job-status polling. **BullMQ + bull-board** gives you durable async orchestration plus an instant queue admin UI for debugging demo failures. **fastify-type-provider-zod** lets you turn Zod into request validation and OpenAPI docs in the Fastify stack you already use. **Vercel AI SDK Core** is the cleanest Node/TypeScript option for structured object generation if you can run Node 22; otherwise a thin Ark provider adapter around your existing `packages/ai` is the safer fallback. **Recharts** is the fastest dashboarding choice for the mock analytics panel. citeturn7view0turn10view2turn9view0turn11view0turn14view0turn15view4turn15view5turn23view0turn13search1

The tools I would **not** introduce right now are equally important. ## Immediate Architecture-Fit Recommendations

For the **frontend**, your repo is already pointed in the right direction: `@dnd-kit/*` is in place for sortable interactions, TanStack Query is already installed for server-state sync, and Tailwind is already the styling base. That means you should **not** spend time swapping in Redux, XState, or a new design system during the hackathon window. Instead, add **Uppy** for the asset ingest surface, use **React Hook Form + Zod** for upload metadata, product forms, and script-generation parameters, and keep storyboard editing intentionally simple: a reorderable list or card board first, not a full NLE timeline. For preview/export, because the current flow generates a single short video per request, a normal video player plus metadata-side editing is sufficient for P0; the value is in orchestration and merchant workflow, not local rendering complexity. citeturn4view1turn7view0turn10view2turn9view0turn11view0turn28search1

For the **backend**, treat **BullMQ as the async transport** and **Postgres `GenerationJob` as the product source of truth**. BullMQ’s own docs expose a clear job lifecycle, progress updates, flows, and queue events; use those features, but persist the user-visible status, current step, retry count, and error summary in Postgres so the polling API never depends on Redis internals alone. The most practical pattern for your case is `jobId = generationJob.id`, `job.updateProgress({ step, percent, traceId })` inside processors, `QueueEvents` for lifecycle hooks, and **bounded concurrency** for remote video generation jobs so one merchant’s failed run cannot stall the entire server-embedded worker. Mount **bull-board** on a protected route so the team can inspect stuck, delayed, retried, and failed jobs during the demo. citeturn40search15turn40search2turn40search3turn40search1turn15view4turn20search1turn14view0turn5view0

For **request validation and API docs**, the best fit is to move harder toward **Zod-first contracts**. Your server already depends on Fastify, `@fastify/swagger`, and Zod, and `fastify-type-provider-zod` is specifically designed to bridge Zod schemas into Fastify validation and Swagger generation. That gives you one schema source for DTOs in `packages/shared`, typed request/response contracts in `apps/server`, and optionally generated client types for the web app later. This is especially valuable because your P0 objects — `Product`, `Asset`, `GenerationJob`, `Script`, `StoryboardShot` — are exactly the sort of payloads that drift fastest when teams move quickly. citeturn5view0turn15view5turn20search2

For **file upload and object storage**, use a two-stage approach. In **P0**, server-stream uploads through `@fastify/multipart` into MinIO/S3 are fine and low-friction; the plugin supports stream mode, per-request limits, and multipart handling in the Fastify stack you already use. In **P1**, switch to presigned uploads so large asset videos go browser-to-object-store directly, while your Node server only issues signed URLs and records metadata. Because MinIO’s JS client is explicitly aimed at S3-compatible object stores, and AWS’s v3 presigner has first-party docs for signed upload URLs, you can implement this without locking yourself to one vendor. citeturn18view0turn21search2turn19view1turn17search11turn17search3

For **logging and observability**, do not add another logger. Fastify already uses **Pino** when logging is enabled, and Pino’s own positioning is high-throughput JSON logging with low overhead. Add structured child loggers with `requestId`, `jobId`, `productId`, `merchantId`, and `traceId`; then layer **OpenTelemetry JS** later for distributed traces, because OTel is vendor-agnostic and supports automatic instrumentation in Node. For AI-specific traceability — prompt versions, model calls, parsed output, retries — **Langfuse** is the strongest open-source addition, but it is a P1 tool, not P0, because it adds another service and UI to run. citeturn17search1turn19view3turn20search3turn16view0turn16view2turn16view3

## AI, Agent, Retrieval, and Media Decisions

Your model provider choice is the hidden advantage here: **Volcano Ark is OpenAI-compatible**, and the AI SDK ecosystem explicitly supports OpenAI-compatible providers. That means you do **not** need to adopt a heavy agent framework to get reliable structured outputs. The cleanest design is: define Zod schemas in `packages/shared`, define prompt templates and normalizers in `packages/ai`, call Ark through either **Vercel AI SDK’s OpenAI-compatible provider** or a thin custom adapter, and validate every response before it becomes a `Script` or `StoryboardShot` record. One pragmatic caveat is that current AI SDK docs say local development needs **Node 22+**; if your runtime or deployment target is still below that, the right move is not to force the upgrade for the hackathon, but to implement a narrow Ark client in `packages/ai` and keep the same schema/repair loop. citeturn28search3turn27search7turn27search1turn23view0turn25view2turn25view3

For **structured JSON reliability**, a boring workflow wins: first-pass object generation against a strict schema, immediate Zod validation, one repair pass if parsing fails, and storage of both the raw model result and the normalized parsed object for debugging. AI SDK Core supports schema-constrained object generation; LangChain JS also supports structured output with Zod and JSON Schema. In your architecture, however, **LangChain is only worth introducing when you start needing tools, retrievers, or provider-agnostic chains beyond simple request/response workflows**. Right now, script generation and storyboard generation are deterministic enough that the lighter choice is better. **LangGraph** is even farther out: its own docs position it around durable execution, memory, and human-in-the-loop agent orchestration, which matches your P2 “Agent orchestration” goals but not your P0/P1 delivery pressure. **BAML** is promising if schemas, retries, and prompt versioning become a genuine pain point, but it adds a new DSL/codegen workflow your team does not need on day one. citeturn22search0turn22search1turn25view4turn25view5turn22search2turn25view0turn25view1

For **retrieval**, the most architecture-aligned answer is **Postgres-first**. `pgvector` lets you keep vectors in the same system of record as your products, assets, tags, and jobs, while retaining ACID semantics, joins, and ordinary Postgres operational habits. For a three-person team, that usually beats spinning up a dedicated vector service early. If you do **not** have a stable embedding model yet, you can still ship useful retrieval in P0 by storing LLM-generated or merchant-supplied tags in `jsonb`, building a generated search column, and indexing with **full-text search** and **`pg_trgm`** for fuzzy lookup. Postgres docs support all of those pieces directly. Move to `pgvector` in P1 when the tagging surface stabilizes. Consider **Qdrant** only when you need stronger payload filtering, hybrid lexical+dense retrieval, or when vector search starts to dominate query patterns. Avoid **Milvus** until you actually need distributed scale. Be careful with **LanceDB** in this codebase: it is attractive for embedded multimodal search and has TypeScript support, but its local-/file-oriented operational model is less aligned with your Postgres-centric system-of-record, and recent open issues around concurrent writers in the JS path are a real warning sign for a server-backed transactional app. citeturn35view0turn39search0turn39search1turn39search2turn39search3turn36view0turn37view0turn38search8turn37view1turn37view2turn37view3turn34search19

For **media**, the most important conclusion is that your current product goal removes much of the reason to build a local media pipeline at all. Official Seedance materials emphasize multi-shot video generation and whole-video generation from text or image inputs, which fits your “single 12s whole-video call” constraint. So in P0/P1, focus on preview, progress, and export UX — not on FFmpeg-based composition. If you later need subtitles, BGM fallback, or lightweight muxing, add **native server-side FFmpeg** and invoke it from Node; FFmpeg’s own docs and README cover multiplexing, filtering, subtitle handling, and multiple inputs/outputs. By contrast, **ffmpeg.wasm** is still labeled experimental and its own performance docs say it will not perform as well as native FFmpeg. **WebCodecs** is powerful but very low-level and not baseline across major browsers. **MoviePy** is a respectable Python automation library, but it is the wrong runtime choice for this Node-first system unless you explicitly decide to add a media microservice later. **Remotion** should be treated as a future layer for template-driven intros/outros, subtitle-overlaid variants, or storyboard preview experiments, not as the engine you build P0 around. citeturn28search1turn28search4turn28search13turn32search6turn32search10turn32search11turn32search12turn31view1turn33search7turn29search3turn29search11turn29search6turn30view0

## Phase Recommendations

**P0 should optimize for end-to-end demo success, not architectural purity.** I would keep the current monorepo shape and current core stack, add **Uppy** for merchant asset upload, add **React Hook Form + Zod** for upload/product/script forms, keep the existing **dnd-kit** board UI for storyboard ordering, keep **TanStack Query** polling for job status, formalize the server contract with **fastify-type-provider-zod**, and wire **BullMQ progress + bull-board** so everyone can see what the system is doing. On the AI side, I would use **schema-validated structured outputs** via AI SDK Core if Node 22 is available; otherwise, I would use a thin Ark client plus Zod validation and a single repair retry. On the data side, I would **not** add vectors yet unless an embedding model is already ready; use tags + Postgres FTS + `pg_trgm` first. citeturn7view0turn10view2turn4view1turn11view0turn15view5turn40search2turn15view4turn27search1turn39search0turn39search1

**P1 should harden the demo path and add the features users will actually touch.** That is the right time for **presigned object-storage uploads**, **pgvector** for embedding search, **Langfuse** for model-call traces and prompt versioning, **Recharts** for the mock data dashboard, and optionally a **Remotion Player** or reference-based lightweight editor view if you want richer storyboard or per-shot previews without yet owning rendering. It is also the point where **Zustand becomes optional**, but only if the creation editor develops enough cross-panel client state that component-local state becomes painful; until then, adding a global client store is probably unnecessary. citeturn17search11turn35view0turn16view2turn11view4turn29search4

**P2 is where you can justify additional systems because they support productionization rather than demo optics.** That includes **server-side FFmpeg** for subtitle muxing and BGM fallback, **Qdrant** if retrieval semantics outgrow Postgres, **OpenTelemetry** as a broader trace/export standard, **LangGraph** if you truly implement agent orchestration or human review nodes, and **Apache ECharts** if the attribution or A/B visualization requires Sankey/funnel/advanced interaction beyond what Recharts provides quickly. This is also the only phase where a real compliance review pipeline starts making sense, because before that the bigger risk is failing to complete the generation flow at all. citeturn32search12turn37view0turn16view0turn25view5turn11view3turn13search2
